# 2026-08-11: a thousand tenants on eight cores, and what eager attach costs

The M3 load test asks one question: put a thousand small projects on one 8 vCPU node, hold a hundred of them attached, and say what the p99s, the attach churn and the memory ceiling are.
This is that run, twice, because the first pass measured the wrong thing and the second one shows why.

One box.
gamingpc, i9-13900K, 32 threads, 32 GB, Ubuntu 26.04 under WSL2, store on local disk.
The node is pinned to cpus 0-7 with taskset, so the eight cores are the deployment being measured and the harness generating traffic is not sharing them.
The box was also carrying the owner's `java` and `llama-server` the whole time, both idling in single digit percent of the other 24 threads.
Nothing is simulated, and the store is a local directory rather than an object store, so these are the node's numbers and not S3's.

Both runs are the same thousand tenants against the same store, `--cpus 0-7 --jobs 8`, 100 attached at once, `shared_buffers` 16MB per tenant, 16 clients, a 300 s measured window capped at 200 rps, then 300 s idle, then a 300 s churn window drawing from all thousand.
The only difference is warmup: 30 s in `fleet-1000`, 600 s in `fleet-1000-warm`.

## Provisioning

| tenants ready | made this run | jobs | tenants per minute | cold create p50 | first request p50 | first request p99 |
|---|---|---|---|---|---|---|
| 1000 | 63 | 8 | 36.2 | 2.674 ms | 13.0 s | 19.7 s |

Registering a ref is a small write and costs milliseconds.
Everything else in first request is initdb, the genesis capture, and the first attach, eight of them at a time on eight cores, which is where the 13 s median comes from.
A thousand tenants is a bit under half an hour of that, and it is written down as it goes, so the run that finally completed skipped the 937 that earlier passes had already built.

## Steady, the same window measured twice

| run | warmup | requests | errors | rps | p50 ms | p90 | p95 | p99 | max |
|---|---|---|---|---|---|---|---|---|---|
| fleet-1000 | 30 s | 507 | 64 | 1.69 | 1.389 | 1806 | 6507 | 10786 | 11603 |
| fleet-1000-warm | 600 s | 59999 | 0 | 200 | 0.715 | 0.994 | 1.077 | 1.298 | 4.251 |

Same node, same hundred tenants, same request mix.
The first row is not a steady state, it is an attach storm: the node reports 100 successful attaches inside the measured window at a mean of 6.209 s each, which is the entire working set being attached while the clients wait for it.
Sixteen clients closed loop at a mean latency near ten seconds is 1.69 rps, and the 64 errors carry the harness deadline text, which the client produces for both its own 60 s timeout and the phase cutoff at 300 s, so the result file cannot tell those two apart.

The second row is the node the question was about.
Warmup at 600 s outlasts attaching a hundred tenants, so the measured window opens with all hundred already up, and then a thousand tenant node answers the full 200 rps the scenario asks for at 0.715 ms median and 1.298 ms p99, sixty thousand requests, zero errors, worst single request 4.251 ms.
The registry served 346644 hits against 1680 misses.
Per request type it is flat: row by pk p99 1.290 ms over 29954 requests, page of 20 p99 1.306 ms over 18044, filtered page p99 1.299 ms over 12001.

The gap between the rows is the whole finding.
A packed node costs nothing to read from once a project is up, and everything about the tail is attach.

## Churn, where attach is the workload

| run | requests | errors | p50 ms | p90 | p99 | max | attaches | attach mean | tenants touched |
|---|---|---|---|---|---|---|---|---|---|
| fleet-1000 | 411 | 27 | 9538 | 15166 | 20119 | 23057 | 375 | 6.209 s | 332 |
| fleet-1000-warm | 695 | 2 | 7617 | 12066 | 18240 | 21897 | 1758 | 7.275 s | 497 |

Churn draws uniformly from all thousand with room for a hundred, so nearly every request is a miss and pays for an attach plus the eviction that makes room for it.
The warm run turned over 1758 attaches in 300 s, 5.9 a second, while holding the gauge at 100, and it did that with two failed requests out of 695.
Registry hits and misses run about even, 1994 against 1910, which is what a uniform draw over ten times the ceiling looks like.

Seven to nine seconds at the median is the honest cost of an attach today, and it is eager: attaching hydrates the database before the first row is served rather than faulting pages in as they are asked for.
Lazy hydrate is the design answer and it is not implemented yet, it sits behind the storage engine redesign.
Until it lands, the number a fleet is sized on is this one, and the sizing rule that follows from it is to keep the ceiling above the working set.

## Memory and disk

| run | rss peak | rss median | rss slope | processes max | disk read | disk write | swap in |
|---|---|---|---|---|---|---|---|
| fleet-1000 | 17.87 GB | 15.88 GB | +929 MB/min | 1178 | 19.4 GB | 39.9 GB | 3148 pages |
| fleet-1000-warm | 15.74 GB | 13.61 GB | -71 MB/min | 1028 | 32.8 GB | 102.8 GB | 24077 pages |

The slope is the whole difference.
The cold run's +929 MB/min is the node filling up from nothing to a hundred attached over a twelve minute run, not a leak, and the warm run says so: over thirty minutes covering warmup, a full steady window, an idle window and a churn window that attached seventeen hundred times, RSS drifts slightly downward and the peak stays under 16 GB.
A hundred attached tenants at 16MB shared buffers, with their backends, settle at 13 to 16 GB across up to a thousand processes, so about 140 MB a tenant, and a node sized for a hundred attached wants 24 GB to be comfortable on 32.
The warm run did swap, 24077 pages in and 17007 out, which is the churn window pushing a 32 GB box with the owner's other work on it.

The store holds 45.6 GB for the thousand, 45.6 MB a tenant, in 4.38 million objects.
The runtime directory, which is what the node keeps locally, ends the warm run at 4.30 GB in 75567 objects while holding a hundred databases.

## Reading

The M3 line asked for p99s, attach churn and a memory ceiling on 1000 tenants over 8 vCPU, and all three have numbers now.
Steady p99 is 1.298 ms at 200 rps with no errors, churn p99 is 18.2 s, and the ceiling is a 15.7 GB peak that does not climb.
Two of those are good and one is a design debt with a name.

The methodology note worth carrying forward is the first row of the steady table.
A 30 s warmup against a working set that takes ten minutes to attach does not measure a warm node, it measures the attach storm, and it reports a p99 three orders of magnitude off.
`fleet-1000-warm` is in the repo so the honest window is the default one to reach for, and the README now says how to size warmup.
