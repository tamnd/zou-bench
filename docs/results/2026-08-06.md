# 2026-08-06: warm REST reads, zou against PostgREST on vanilla Postgres 18

The M2 exit line asks for a warm REST read p50 under 5 ms and a p99 under 25 ms on a single node with a small tenant in RAM.
This is that measurement, and next to it the same scenario asked of PostgREST 14.16 over a stock Postgres 18.4, which is the thing zou claims to answer like.

Box: gamingpc, i9-13900K, 32 threads, 56 GB, Ubuntu 26.04 under WSL2, otherwise idle.
The other three boxes were carrying the user's own work during this window, load 2.7 to 23 on 4 to 8 cores, and a latency target measured against someone else's compile is not a measurement.
An earlier run on server3 at load 23 gave p50 11.8 ms and p99 85 ms, which says what the box was doing rather than what zou does.

Setup, identical on both legs: `scenarios/rest-demo.sql`, 200 lists, 20000 todos split between two owners behind an RLS policy, 1000 public notes, one rpc, `analyze` at the end.
Scenario `scenarios/rest-warm-reads.json`, 8 clients, 15 s warmup discarded, 60 s measured, driven by `zoubench rest` over keep alive connections.
Store on local disk, no `ZOU_STORE_SIM`, so nothing here is simulated.
zou answers under `/rest/v1`, PostgREST at the root, which is the whole reason the scenario carries paths without an api prefix.

## Reading

NFR-10 asks for p50 under 5 ms and p99 under 25 ms.
zou measures 0.811 and 2.634, so the target is met with an order of magnitude of room, and the slowest single request in the whole run was 6.5 ms.

Against PostgREST, zou is 0.77x the throughput and about 0.2 ms behind at the median.
Per shape the tails are the more interesting half: zou's p99 is lower than PostgREST's on four of the seven shapes, including all three of the plain reads, and its worst request of the run was 6.5 ms against PostgREST's 9.0.
The medians are consistently PostgREST's, by 0.1 to 0.2 ms.

The one real gap is the rpc: 2.43 ms against 0.997, and it is the only shape where zou is more than 0.3 ms behind.
Nothing else in the run separates the two by that much, so it is the function call path rather than anything about reading rows.

Two numbers on the side worth keeping.
zou served the run on 2 postgres backends where PostgREST used 10, and the postgres process tree burned 31 CPU seconds against PostgREST's 276, which is 67 us of server CPU per request against 460.
zou's peak RSS was 841 MB against 327, which is the page cache it keeps and expects to keep.

The CPU and RSS figures come from sampling the process tree under the data directory, so they cover postgres and not the http server in front of it, which on the zou leg is the same process and on the PostgREST leg is a separate one.
Treat them as a comparison of what postgres was asked to do, not of total machine cost.
