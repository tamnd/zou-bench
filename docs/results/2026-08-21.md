# 2026-08-21: the rpc shape, before and after zou stopped introspecting per call

The 2026-08-06 run found one shape where zou was more than 0.3 ms behind PostgREST: the rpc, 2.433 ms against 0.997 at the median, in a scenario where every other shape was within 0.2 ms.
That became tamnd/zou#178, and the cause was that `/rpc/<name>` asked postgres what the function looked like on every call while the read path took its catalog off a cache held for the life of a schema epoch.
tamnd/zou#560 moves the function introspection into that cache.
This is the before and the after, with a PostgREST leg run in the same window so the reference comes from the same box on the same day.

## The box, said up front

gamingpc, a 13th generation Core i9-13900K, 32 threads, Ubuntu 26.04 inside WSL2.
Two things differ from 2026-08-06 and both make the absolute numbers slower: WSL2 has 31 GB now where it had 56, and the box was carrying about 2.5 of load rather than being idle.
That is why row-by-pk reads 2.08 ms here against 0.737 on 2026-08-06.
It does not touch what this day is for, which is two zou binaries measured against each other within minutes of one another on one box, alternating, twice each.

Setup and scenario are unchanged from 2026-08-06: `scenarios/rest-demo.sql`, `scenarios/rest-warm-reads.json`, 8 clients, 15 s warmup discarded, 60 s measured, a fresh store per leg.
The zou legs are `zou dev` at tamnd/zou 47e80ea (before) and at the head of tamnd/zou#560 (after), release builds of the same tree otherwise.
The PostgREST leg is 14.16 over a stock Postgres 18.4 with a pool of 16, the same pairing 2026-08-06 used.
No leg recorded a failure, and every request in every leg answered with the status the scenario expected.

## Reading

The rpc drops 1.78 ms at the median and 2.02 ms at the tail.
The other six shapes move by 0.02 to 0.05 ms and not all in the same direction, which is what a scenario looks like when one request in seven stops holding a connection for two extra milliseconds.

The useful comparison is against zou's own cheapest read rather than against PostgREST, since this box is slower today than the one 2026-08-06 measured.
An rpc used to cost 2.35 ms more than a row by primary key and now costs 0.59 ms more.
PostgREST's own rpc premium on the same box in the same window is 0.49 ms.
So the shape that was an outlier now sits the same distance off a plain read as the reference implementation's does, and what is left between the two legs is the 0.7 ms zou is behind PostgREST on every shape here.

At the run level: p99 4.78 to 3.92, throughput up 6.5 percent, and server cpu per request from 680 to 577 microseconds.
That last one is the clearest statement of what was removed.
Only one request in seven is an rpc, so a hundred microseconds off the average is about seven hundred off the rpc, which is a recursive walk of `pg_type` planned and executed once per call and now once per schema epoch.

## What the store did, which is nothing

The op counters are in these results and they are the same on both legs: 675 to 682 gets, 582 puts, 47 compare and swaps over a whole run, every smgr read served from the local page cache, zero io errors, zero CAS conflicts.
That is the check that this change is what it claims to be.
The query that went away was a query, so the store should not be able to tell the difference between the two legs, and it cannot.
