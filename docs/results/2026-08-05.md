# 2026-08-05: S1 exit gate reruns after the relation size cache

Build under test is zou at 561f80f plus patch 0004 from tamnd/zou#156, the shared memory relation size cache in the smgr shim.
Before that patch the planner paid a store GET for the size of every table and index it planned over, on every query, which multiplied each statement by the store latency.
These are the reruns for the S1 exit box on tamnd/zou#62.

Setup, same on both boxes: pgdata and the store both on /dev/shm so local disk fsync stays out of the numbers, initdb with io_method=sync, scenario scenarios/commit-8c.json (single row UPDATE, 8 clients, 4 threads).
The s3-express leg runs the sequencer window at ZOU_WAL_WINDOW_MS=1, the other legs use the 3 ms default.
A window sweep on server3 gave express p50 11.65 ms at 3 ms, 9.55 at 1 ms, 9.62 at 0.5 ms, so 1 ms is where it settles.
All s3 latencies come from ZOU_STORE_SIM profiles and every such row is stamped (sim); tmpfs rows are real hardware with no store delay.

Boxes: server3 is 8 vcpu AMD EPYC, 23 GB, with one unrelated process pinning a core the whole time.
server2 is 6 vcpu AMD EPYC, 11 GB, and carried background load around 2.7 during the runs, so treat its tails as noisy.

pipe_bench drives the group commit chain through the real C ABI with no Postgres on top, so these are the floors the real server can approach but not beat on each box.
The server3 protocol legs above predate the 1 ms window change, they ran at the 3 ms default.

## Reading

The gate asks for commit p50 under 10 ms on express and under 60 ms on standard at 8 clients.
server3 makes both: 9.75 express, 40.63 standard.
server2 makes neither, but its own protocol floor already sits at 14.31 ms on express, so the miss there is the box, not the design; real pg lands within 1.5x of the floor on every profile on both machines.
The request ceiling is visible in the store op counters inside the raw jsons: the server3 express leg served 44452 transactions on 12012 chain CAS writes plus 365 page PUTs and 586 page GETs, about 3.7 commits per store write, and the GET count no longer scales with the query count.

Before and after the size cache, server3 p50: tmpfs 6.22 to 5.97, express 20.91 to 11.72 at the 3 ms window, standard 107.73 to 45.24.

Raw jsons stay out of git per the result book rules; scenario file plus this table reproduces the runs.
