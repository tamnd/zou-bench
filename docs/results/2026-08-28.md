# 2026-08-28: the two read paths, with the bill attached

zou has two ways to answer a page read and until today the result book compared them with one number each.
The object path (`ZOU_PAGESERVE=0`) writes a page object per page and reads a page object per miss.
The layer path (`ZOU_PAGESERVE=1`) writes neither and asks a page service, which reads the layer objects instead.
On pgbench scale 10 the object path finishes 3.5x the read only transactions, and quoting that on its own was the problem tamnd/zou#672 was opened about, because the same pair of runs has the layer path loading the database twelve times faster and ahead on the write mix.

Both of those are true and neither is a ranking.
This page is the pair of runs with the store counters differenced per phase, so each tps sits next to what it cost.

## The box, said up front

gamingpc, a 13th generation Core i9-13900K, 32 threads, 32 GB, Ubuntu inside WSL2, both stores on a local directory under `/home/zoubench`.
Postgres is the vendored 18.4 with the zou patches, stock initdb plus `io_method=sync` and `full_page_writes=off`, so 128 MB of shared buffers on both legs.
pgbench scale 10, which is about 160 MB of data, 4 clients, 300 s a phase.
The two legs alternate rather than run back to back, four times each, and the counters below come from the fourth pair.

The harness is `scripts/zou-bench.sh` in tamnd/zou, not `bin/zoubench report`, because this is the storage engine under pgbench rather than the REST door under a scenario file.
As of tamnd/zou#672 that script copies the counter file at every phase boundary and prints the difference under each phase, which is where every number on this page comes from.

## Reading

A page class op on the object path is a page.
24.7 GiB over 3238099 ops is 8192 bytes each, to the byte, in the read only phase.
A page class op on the layer path is not: 4.2 MiB over 511063 ops is under nine bytes each, which is the relation length record filed under the same prefix, and the pages themselves stay inside the shard layer objects that the page service reads on the far side of the socket.
So the read only phase pushed 25 GB through the store on one path and 4 MB on the other, and the path that pushed 25 GB is the one that finished 3.5x the transactions.
That is the trade stated plainly rather than as a ratio: the object path buys a 16 microsecond read by writing every page it might later want, and the layer path declines to write them and pays a millisecond through the service when it wants one back.

Load is the same trade seen from the other end and it is the loudest cell on the page.
76 seconds against 6, 359 MiB of pages written against 23 MiB of length records, and it is the same 28801 reads on both legs.
The object path is writing the whole loaded database out as page objects while it loads, which is exactly the work that makes its reads cheap later, and the layer path defers it into 264 MiB of shard layers that the page service builds behind the load.
Shutdown says it a third time: the object path flushes a last 128.7 MiB of pages, the layer path has no dirty page to flush and writes 206 KiB.

The write mix is where the deferral pays off inside the same run.
The layer path writes 46 MiB of page class records against 530 MiB, halves its wal traffic, and comes out at 366 tps against 335, and this is with the layer path's reads still costing 2048 microseconds at the median against 32.
So on a write heavy mix the read penalty is not the deciding term, because most transactions find their page in shared buffers and never ask.

Which one to run is a question about the tenant, not about the paths.
A tenant that loads a lot, writes steadily, and reads a working set that fits in its buffers wants the layer path: seconds to load rather than minutes, ahead on the write mix, and paying the socket only on a miss.
A tenant that writes rarely and reads widely wants the object path, because a miss is 16 microseconds there and a millisecond on the other, and 3.2 million misses in five minutes is the entire distance between the two read only numbers.
Scale 10 select-only is the second shape at its most extreme, since the database is 160 MB and a miss is cheap for everybody, which makes it the phase least entitled to speak for either path.

## What is still owed

The service tier median of 1024 microseconds is a wait rather than work.
tamnd/zou#695 took the parked read poll from 100 ms down to a millisecond, which is the 4.6x on the write mix already in the book, and what is left is a read position that is one lsn for the whole cluster instead of one per block.
tamnd/zou#671 stays open until that tail is inside a millisecond and tamnd/zou#697 is the per block position that would get it there.
Until then the layer path's read column is measuring a poll interval as much as it is measuring a storage design.

Counter files for both legs, one per phase boundary, are under the run directories on gamingpc.
The phase lines quoted above are the output of `zou stats <file> --since <earlier> --brief` and can be re-derived from those copies without rerunning anything.
